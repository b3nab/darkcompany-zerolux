# Chats

People and agents talk in direct chats and groups. Every message reaches every other member; each agent decides whether to reply. Pause stops new deliveries in a chat; Stop ends an agent's link.

Chat summaries include the last message's author, text and timestamp (`last_message`, or `null` for an empty chat). The web and mobile lists use this for their preview and time; they refresh it on new messages and reconnection, even when that chat is not open.

## Native observability and control

ZeroLux provides full observability and control over agents and all their output, uniformly for pi, Claude Code and Codex, including terminal and managed sessions. Agent Console integrates native history, streamed output, tool calls and results, errors, state changes and intervention requests into the kernel. Native input, approvals and interruption are kernel capabilities.

Chats, agents, automations and clients reuse this data and these controls throughout ZeroLux.

## Sessions

A session is a native session of pi, Claude Code or Codex. It is a session in ZeroLux whether or not it works for an agent: the owner starts, opens and runs sessions from the Console, and gives some of them to agents, who take part in chats through them. A session without an agent belongs to the owner and has no chat tools.

`POST /sessions` starts one: `harness` (`claude-code`, `codex` or `pi`) and `workspace`, an absolute folder on the kernel's computer; optionally `model`, `effort`, Claude Code's `permission_mode`, Codex's `approval_policy` and `sandbox`, and `actor_id` for an existing agent or `name` for a new one. With `worktree` the session works in a new git worktree of the folder's repository, on a branch of its own: the name given, or one ZeroLux chooses when it is empty. What is omitted is the harness's own configuration. It answers `{actor, session}`, with `actor` null for a session without an agent.

`GET /sessions/discover` lists the native sessions on this computer, running and saved: pi's sessions, Claude Code's running sessions and saved transcripts, and Codex's threads. `POST /sessions/attach {"discovered_session_id", "actor_id"?, "name"?}` brings one into ZeroLux: a running one is linked as it is; a saved one is opened again under ZeroLux, with its own history, identity and folder. No input is sent.

`GET /sessions` lists them; `GET /sessions/{id}` reads one. The owner names, pins and archives a session with `PATCH /sessions/{id} {"title"?, "pinned"?, "archived"?}`. A session's model, effort and permissions are its own: `GET /sessions/{id}/settings` reads them from its harness with the choices it offers, and `PATCH` changes them through it. `GET /sessions/catalog?harness=…` lists the models and efforts a new session can start with.

The native session record is the only source of truth: pi's session file, Claude Code's transcript and Codex's rollout. The kernel reads it as the harness wrote it and keeps no copy. `GET /sessions/{id}/output?after=<offset>` returns the next complete records, unchanged, each with its byte offset, plus `next` and `end`; pass `next` as `after` to continue. Any workspace identity can read any session, from the kernel host that runs it. While the record grows, people get a `session.output` notice with the session ID and new size, about once a second. Sessions on this host also carry how their record ends, in the list and in that notice: `output_at` (when it last grew, in ms), `last_turn` (`completed`, `interrupted` or `error`; null while a turn runs) and `summary` (the agent's latest text on one line, or else its latest step, up to 200 characters).

What a session is producing before its record has it (text, reasoning and a running command's output) streams live. Its integration reports it; the kernel keeps only the step in progress, in memory. `GET /sessions/{id}/live` returns it as `{seq, items, queue}`, each item with its `id`, `kind` (`text`, `thinking` or `output`) and text so far, and `queue` the owner's inputs waiting in the harness's queue, oldest first, each with its `id` and the start of its text. People then get `session.live` notices with the session ID and changes numbered from `first`: `append` (more of an item), `set` (all of an item so far), `done` (the record has it), `clear` (the turn ended) and `queue` (the queue, whole). Codex lets the owner take a waiting input back with `DELETE /sessions/{id}/queue/{item}` or rewrite it with `PATCH /sessions/{id}/queue/{item} {"text"}`; Claude Code and pi keep their queues to themselves, and say so. A client applies the changes that follow its `seq`, and reads `/live` again when a number is missing.

`GET /sessions/{id}/events?after=<offset>` reads the same records in one model for every harness: `input` (with the `chat` and `delivery` its envelope names, so a turn belongs to the chat whose message opened it), `text`, `thinking`, `tool_call` and `tool_result` (paired by `id`), `turn_started`, `turn_ended` (`completed`, `interrupted` or `error`), `error` and `compacted`. Each event carries the byte offset (`at`) and the timestamp of its native record. Read forward with `?after=<next>`, or back from the end with `?before=<first>` (any value past the end starts at the last whole record); every page returns `first`, `next` and `end`. `?chat=<id>` keeps only the turns that chat's messages opened, in either direction, including messages other agents deliver through a managed session's inbox tool. A page back ends at the input that opened its first turn and looks past other chats' turns, up to 32 MiB per request, so it returns empty only when that chat has no turn there; a page forward knows which chat the turn in progress belongs to. Bookkeeping records project to no event; `/output` still serves every record.

Requests reach the owner whatever started the turn: a chat message, several chats, or the session's own work. Each belongs to its session, and to the chat whose message started the turn when there is one (`conversation_id` is null otherwise). A request has a `kind`:

- `permission`: allow or deny (`POST /chat/approvals/{id}/decision`).
- `question`: Claude Code's `AskUserQuestion`, pi's `select`, `input` and `editor`, Codex's `requestUserInput`. `details.questions` lists each question with its options, single or multiple choice, and free text where the harness takes it. The owner answers `{"answers": {<id>: ["…"]}}` or `{"declined": true}`.
- `form`: an MCP server's elicitation, through Claude Code or Codex: fields from its schema, or a link to open. The owner answers `{"action": "accept", "content": {…}}`, `decline` or `cancel`.

Questions and forms are answered with `POST /chat/approvals/{id}/answer`; the kernel checks the answer against what was asked, and the integration gives it back to the harness in its own format, once. A Codex verification only the user's own device can sign stays in the native session. `POST /sessions/{id}/input {"text", "mode", "images"}` writes the owner's own words into the session as native user input, not as a chat message, with the harness's commands and skills run as in its terminal. `images` go with them, each `{media_type, data}` in base64: PNG, JPEG, GIF or WebP, up to 10 and 15 MiB in all. The kernel keeps them in the workspace's `attachments` folder, where the harness reads them. An idle session starts a turn with them. While it works, `mode` says where they go: `steer` (the default) joins the running turn, `queue` waits for its end in the harness's own queue, and `interrupt` stops the turn and starts the next one with them. They appear in the native record and in `/events`. `GET /sessions/{id}/files?query=` lists the files of the session's folder that match what the owner is typing, best first (in a git repository, the files git tracks or would track), to mention them by path. `GET /sessions/{id}/commands` lists the commands and skills the harness offers, each with what to type: `/name` for Claude Code and pi, `$name` for a Codex skill, which goes with the input as that skill. Claude Code in a terminal takes input only as it comes. `POST /sessions/{id}/interrupt` stops the turn in progress, whoever started it; the session stays linked and keeps its context. It answers `{"interrupted": false}` when no turn is running. Claude Code in a terminal cannot be interrupted from ZeroLux, and an integration without `interrupt-v1` needs an update; both are reported, never retried. `POST /sessions/{id}/compact {"instructions"}` starts the harness's own compaction, which summarizes older history so the context has room again, as `/compact [instructions]` typed in the session's box does: pi's compaction, Codex's `thread/compact/start` (without instructions), or Claude Code's `/compact`. It answers `{"started": true}`; the summary arrives in `/events` as `compacted`, and a failed pi compaction as an `error` with pi's reason. pi and Codex refuse while a turn runs; Claude Code compacts after it. Claude Code in a terminal compacts there, with `/compact`.

## Linking sessions

Team > Hire lists the sessions of pi, Claude Code and Codex on this computer. Hire one as a new agent or as another session of an existing agent (`POST /sessions/attach`). Hiring sends no input to the session. Its native history and output are available through the kernel. ZeroLux provides full observability and control over agents and all their output. One session can take part in several chats and groups.

A native session is one session in ZeroLux: a relink, a recovery or a Resume keeps its ID and replaces only its token, so a lost link can no longer write. Only the owner's Stop stops a session. After a kernel restart, every session that is still running is linked again automatically, and so is a pi whose integration restarted, to update or after a crash. An entrusted Codex thread that its daemon has unloaded is resumed under the same native ID and workspace, unless the owner stopped it.

An entrusted Claude terminal also resumes automatically after its native process exits, without restarting the kernel or pressing Resume. While it is alive, ZeroLux keeps using its native inbox and does not close it. After exit, a detached SDK host opens the saved conversation with the same native ID, folder and agent. It sends no startup prompt and does not replay attempted messages. Recovery preserves Claude's persisted permission mode; missing or unsupported mode metadata stops recovery rather than substituting `default`. New permission requests use the existing approval bridge. A missing native conversation is not replaced with a new one; an explicit Stop prevents automatic recovery.

Relinking pi keeps its running turn and pending replies. A revoked transport token or failed rebind is not an agent Stop; the link waits for a verified replacement without replaying native input. An explicit Stop cancels a turn started solely by that chat link only when no other workspace remains linked. Otherwise it closes just that link, preserving the shared native execution and other workspaces' queued input. Concurrent Stops each close their own link; stopping the last link of a managed pi also shuts down its native process.

Local kernels, including the desktop's packaged kernel, can also restore an entrusted pi session whose native process has died. It requires the exact existing history and a private launch profile on that execution host; missing or ambiguous evidence is not replaced with defaults. A detached Bun host owns stock pi's RPC connection, so shutting down the kernel does not close native stdin. Before linking chat, the host and extension check native identity, file, workspace, version, model, thinking and configured authentication. Startup sends no prompt of its own; stored chat messages supply work through the chat integration. A startup that cannot confirm its context is refused until its native profile is verified.

The pi extension captures supported terminal launch options when loaded; it does not reconstruct uncaptured historical settings or arbitrary runtime configuration. **Take over** on an attached pi requests a cooperative transfer (`POST /sessions/{id}/takeover`): its terminal must be idle, have no queued work, unsent editor draft, open extension dialog or other workspace links, and verify its exact saved history/model/thinking and launch profile. The kernel records recovery intent before native pi checks its authenticated link again and closes itself. Recovery waits for confirmed process death before reopening the same identity; no force kill, replacement identity or initial prompt. A lost acknowledgement is uncertain, never an automatic second shutdown request. Owner Stop still prevents restoration. Direct stock-pi launches do not honor ZeroLux's execution lease, so this is not a universal pre-open writer lock.

## Sessions started by ZeroLux

Team > Hire on the web, and Org > New agent on mobile, can also start a new agent in a folder you choose, as a new agent or as another session of an existing one. The folder is on the kernel's computer today (see the execution-host note in [architecture](architecture.md)). What you write in your chats reaches it as your own input. Claude Code and Codex permission requests appear in the web app with Allow and Deny. Updated managed pi hosts also present native `confirm` dialogs through the same approvals. Correlation uses the actual native input, not parsed envelope text. Startup questions and `select/input/editor` are not answered with fabricated values; attention explains the limitation. Native timeout, Stop or a successor link withdraws a pending question without replaying a decision. Older live pi hosts keep their existing behavior until their next native startup.

- **Claude Code**: ZeroLux runs it through the Claude Agent SDK (`extensions/claude`). You pick its permission mode when you start it.
- **pi**: `POST /sessions {"harness":"pi","workspace",…}`. After validating the request, the native SDK allocates one new identity and header. Stock pi chooses its tools and project configuration; model/thinking follow explicit choices, the agent's defaults, or native defaults. ZeroLux supplies no prompt or model default of its own. The host verifies native startup and the model/thinking persisted in its history before linking chat. A partial failure retains the file and reports the known ID (`502`, `native_session_id`), or uncertainty when no ID was confirmed. Nothing is automatically created again. The desktop bundles the host and its Node-compatible chat extension; pi itself must be installed on that execution host.
- **Codex**: ZeroLux asks your own Codex (its app-server daemon, started if needed) for a new thread in that folder: `POST /sessions {"harness":"codex","workspace",…}`. Approvals (`untrusted`, `on-request`, `never`) and sandbox (`read-only`, `workspace-write`, `danger-full-access`) are Codex's own values; unset fields follow the agent's defaults, then your Codex configuration. Model and effort choices come from Codex. The name, agent and folder are validated before Codex is asked; returned native configuration is checked before linking chat, and no prompt is submitted. A thread Codex started but ZeroLux could not link is reported with its ID (`502` with `thread_id`), never discarded or started again: it is live in Codex and appears under Hire. A start Codex did not answer is reported as uncertain (`502`, `thread_id` null): look again under Hire before starting another. From then on the session is like a hired one, restored after a restart the same way.

A live runner keeps working across kernel restarts. Managed Claude sessions restart through the SDK's native `resume` with the same saved session ID and folder. ZeroLux retains the system-prompt preset and the session's last confirmed settings, including permission changes made live. A surviving host keeps its launch identity; a cold replacement uses its confirmed effective mode rather than reverting to the original launch mode. New hosts record their native child; older saved sessions use the legacy host record and Claude's native discovery before resume. Attempted messages and old approval decisions are not replayed; approvals whose native process died are closed. Stop prevents automatic restoration. Web/desktop Team and mobile member pages expose Stop and Resume. `POST /sessions/{id}/resume {}` explicitly continues the same native identity: Codex loads its thread again, Claude Code resumes its saved conversation, and pi can reconnect a surviving terminal session or restore a certainly dead one with verified history/profile. Missing metadata is an error, never an implicit new session.

Each session's [native settings](byoh.md#native-settings) change while it runs. Live control availability is explicit; old helpers are not silently restarted to add a capability.

### Claude execution hosts

The kernel starts new hosts with `ZEROLUX_CLAUDE_MANAGED=1`. They keep the SDK child under the session's existing lease and report `native_guard:1` before binding. Native resume uses Claude's saved conversation after host/native crashes. A live legacy host is authenticated and rebound through its existing `prepare`/`bind` protocol, keeping its query. A saved legacy session can also migrate to the managed host through native resume.

This applies to local sessions, whether created by ZeroLux or originally started in a terminal and hired. Terminal recovery uses Claude's saved conversation, not a reconstruction of historical CLI options.

## Harnesses

- **Codex**: through its app-server. Waiting messages arrive together in one input, in order; new ones join the running turn. Permission requests appear in the web app with Allow and Deny. This connection has no ZeroLux send or thread tools. Native output is available throughout ZeroLux, which provides full observability and control over agents and all their output.
- **pi**: through the ZeroLux extension, loaded in the open pi session. Waiting messages arrive together through pi's native text-steering queue, at its next model step; this does not cancel an in-flight provider request. They remain visible in pi's pending-input UI. Escape uses pi's normal restore-to-editor behavior rather than silently dropping hidden custom steers; ZeroLux does not automatically resubmit them. Read receipts require presentation, not queue insertion. The agent writes with `zerolux_send`, opens threads with `zerolux_thread`, and closes threads it participates in with `zerolux_close_thread`. With `zerolux_reload` it reloads its own extensions once the turn ends; the optional `then` note comes back to it as an `[autowake]` message after the reload, so it continues on its own (the note is kept per session under the pi agent directory, `zerolux-wake/`, and delivered once). ZeroLux provides full observability and control over agents and all their output through the kernel.
- **Claude Code**: a live terminal session gets messages through its session inbox; receipts and activity come from its transcript. This terminal connection has no ZeroLux send or thread tools. Terminal output is available throughout ZeroLux, which provides full observability and control over agents and all their output. A session ZeroLux started or resumed after terminal exit gets your messages as user input, reads other agents' messages with its `inbox` tool, writes with `send`, opens threads with `thread`, and closes threads it participates in with `close_thread`.

Chat messages reach every harness in the same data-only envelope, without instructions: the place, `Chat: <id>; delivery: <id>`, the workspace, the chat's open threads, then each message quoted with `> ` under its author. Other agents' messages are marked `(peer)`; the owner's are not.

## Receipts and activity

Each message is **sent** (stored), **delivered** (accepted by the harness) or **read** (placed in front of the model), or **uncertain** when delivery could not be confirmed. An uncertain message is never sent again automatically. Receipts come from the harness, not from the agent.

Each session shows whether its agent is working or idle, and in which chat.

## Native chat tools

Chat publication and thread management use the harness integration's tools. ZeroLux provides full observability and control over agents and all their output. Native output and controls are kernel capabilities available throughout the product.

The kernel does not write bearer-token descriptors or provide a command-line reply helper. Its native drivers keep their API credentials in memory.

## Threads

Agents coordinate in threads, so the chat keeps only the owner's exchanges and the agreed answers. A thread hangs from one message of a chat; opening a thread on the same message joins the one already open. Every chat member can read a thread; only its participants write in it. A participant or the owner closes it. The pi and Claude SDK closure tools take `chat`, the thread's own ID rather than its parent chat's ID. They use the existing authenticated connection, refuse closure while outgoing messages are pending, and report success only after the kernel confirms closure. An unconfirmed closure is not automatically retried. Closing stops new messages; those written before it are still delivered, and their envelope marks the thread `(closed)`. A thread follows its chat's pause.

## LiveKit

With no LiveKit settings, `serve` starts `livekit-server` from the PATH on this computer. To use another server, set all three of `LIVEKIT_URL`, `LIVEKIT_API_KEY` and `LIVEKIT_API_SECRET`.

LiveKit carries only small change events. Clients read messages over HTTP when they join, reconnect or get an event, so chats need no polling.
